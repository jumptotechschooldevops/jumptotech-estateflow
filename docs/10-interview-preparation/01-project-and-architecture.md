## The elevator pitch (practice saying this in under 30 seconds)

"EstateFlow is a property-listing app I deployed end-to-end on AWS EKS — React/Nginx frontend,
Node/Express backend, Postgres for data, Redis for caching, S3 for property photos. I built
the Kubernetes manifests, set up IAM roles for pods using IRSA instead of static credentials,
configured the ALB ingress with proper health checks, and wired up a GitHub Actions pipeline
that builds, scans, and deploys on merge. It's a training-lab project, not a product with
real users, but every piece of infrastructure is built the way I'd build it for one."

## Q&A

**Q: Why store image bytes in S3 instead of the database?**
A: Databases handle small structured rows well; large binary blobs bloat backups, slow
replication, and waste expensive database storage. Object storage like S3 is built for exactly
this, is far cheaper per GB, and scales independently of the database. The database only
stores a pointer (the object key) plus metadata.

**Q: What's a presigned URL, and why use one instead of making the bucket public?**
A: A presigned URL is a normal S3 URL with a cryptographic signature and expiry baked into the
query string, generated by someone who already has IAM permission to access that object. It
grants temporary, scoped access to one object without changing any bucket-wide permission —
the bucket stays fully private even if a URL leaks (it just expires, after which the object is
inaccessible by any other means).

**Q: How do you decide whether to cache a response?**
A: It depends on both read frequency and the cost of staleness. The property list is cached
30 seconds — cheap to recompute, short staleness window is acceptable. Presigned image URLs
are deliberately *never* cached, because their validity window and a cache's TTL could drift
apart and serve a URL that looks valid but has already expired.

**Q: This project uses one shared admin token instead of real user accounts — why, and how
would you fix that for production?**
A: Building a full login system would have been scope creep for a project whose point is
teaching infrastructure, not auth UX. For production, I'd replace it with per-user accounts
(Cognito, Auth0, or a self-issued JWT with a real login flow) and move from "has the token" to
role-based checks — "is this specific user allowed to edit this specific property." The
middleware is isolated to one function (`backend/src/middleware/auth.js`) specifically so that
swap is localized.

**Q: What would you change first if this had to support real production traffic tomorrow?**
A: Real authentication, HTTPS (an ACM cert + 443 listener on the ALB — currently HTTP-only,
appropriate for a lab but not production), real monitoring/alerting (currently proposed, not
implemented — see [08-monitoring-and-observability](../08-monitoring-and-observability/README.md)),
and automated database backups.
