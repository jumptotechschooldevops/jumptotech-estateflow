# 09 · ALB 502, 503, and 504

**Related guide:** [09 · Ingress, ALB, and target groups](../02-deployment-guides/09-ingress-alb-and-target-groups.md)

## Symptoms
Users (or your own `curl`) get HTTP `502 Bad Gateway`, `503 Service Unavailable`, or
`504 Gateway Timeout` from the ALB's DNS name.

## Potential customer impact
Full or partial outage — users cannot load the site or call the API.

## Detection and alerts
`curl -I http://<ALB_DNS>/` status code; CloudWatch ALB metrics if configured (see
[08-monitoring-and-observability](../08-monitoring-and-observability/README.md)).

## Severity assessment
SEV1 if affecting all traffic; SEV2/SEV3 if intermittent.

## Diagnosis (🔍 read-only)
```bash
aws elbv2 describe-target-health --region us-east-1 --target-group-arn <arn>
kubectl get pods -n estateflow-staging -o wide
kubectl logs deploy/backend -n estateflow-staging --tail=100
```

## How to interpret the output
- **502** usually means the target closed the connection unexpectedly (pod crashed mid-request,
  or a readiness probe passed right before the pod died).
- **503** usually means *zero healthy targets* in the target group — see
  [10 · Unhealthy Target Groups](10-unhealthy-target-groups.md).
- **504** usually means a target is healthy but too slow to respond within the ALB's idle
  timeout — check for a slow/stuck downstream call (Postgres, S3).

## Possible causes
- All backend pods crash-looping ([02](02-crashloopbackoff.md))
- All targets unhealthy ([10](10-unhealthy-target-groups.md))
- A slow dependency (e.g. Postgres under load) causing request timeouts

## Safe mitigation steps (⚠️ changes infrastructure)
Depends entirely on the root cause found above — this runbook is a router to the specific
fix, not a standalone mitigation. Common immediate step while root-causing:
```bash
kubectl scale deployment/backend -n estateflow-staging --replicas=4   # more capacity to absorb load
```

## Escalation criteria
Any SEV1 (full outage) — follow
[05-incident-management/02-communication-and-escalation.md](../05-incident-management/02-communication-and-escalation.md)
immediately, don't spend more than a few minutes solo before declaring the incident formally.

## Recovery verification
```bash
curl -I "http://<ALB_DNS>/"             # 200
curl -s "http://<ALB_DNS>/api/health"   # status: ok
```

## Prevention recommendations
Keep readiness probes strict enough to catch a pod about to fail before the ALB routes traffic
to it; set appropriate resource requests so pods aren't starved under load.
